# M0.5 — Reference architecture and M1 decision gates

**Status:** proposal for maintainer review. Evidence reviewed on **2026-11-10**. No OS, Bridge, virtual machine image or runtime proof was built. The package/API facts and their limitations are documented in the [Linux foundation study](M0_5_LINUX_FOUNDATION.md) and [LoopBridge feasibility study](M0_5_LOOPBRIDGE_FEASIBILITY.md). Confidence in the reference combination is **medium** until the experiments below pass.

## Recommended reference architecture

**Start on Debian 13 stable amd64 with a small Sway/wlroots Wayland session and XWayland for legacy apps.** Debian gives the team glibc application compatibility, documented security maintenance, install tooling and packaged graphical components without creating a separate package ecosystem. Use an existing maintained Linux environment for M1. Later, qualify an independently bootable distribution that can run the same agent-facing contract on physical machines and VMs. Ubuntu Server 26.04 LTS with an explicitly curated desktop package set is the viable base fallback. [Base and footprint evidence](M0_5_LINUX_FOUNDATION.md#linux-base).

**Use compositor state for windows and AT-SPI for elements.** An unprivileged session service would normalize Sway IPC and libatspi/D-Bus into separate window and accessible-tree models, with explicit correlation and uncertainty. One synthetic output should keep the same graphical session alive before, during and after human viewing. An independently authorized view-only wayvnc attachment is the first candidate. A separate human input path must preempt the agent on that same session. Verify the availability of compositor-mediated conventional input before advertising it. The Sway portal backend is a candidate for capture and should not be assumed to implement RemoteDesktop or EIS. GNOME Shell/Mutter with GNOME Remote Desktop is the bounded graphics alternative if the Sway path hits a blocking capability gap. [Graphics evidence](M0_5_LINUX_FOUNDATION.md#graphics-and-monitorless-sessions), [accessibility evidence](M0_5_LINUX_FOUNDATION.md#accessibility-as-the-semantic-layer).

**Expose an authenticated local control plane first.** Evaluate gRPC/Protocol Buffers over a filesystem Unix-domain socket, with kernel peer credentials plus a separately enrolled, scoped client identity. If peer credentials cannot be used cleanly through the candidate framework, compare JSON-RPC over a defined local framing. An agent and a human observer have distinct identities, grants and lifetimes. Desktop control, accessible content, pixels, process launch and file operations require separate grants. Session policy, logind, vetted XDG launch targets, `/proc` and cgroups, and systemd's narrow D-Bus interfaces are the initial native integration points. Privileged helpers are a possible later design for specifically authorized administration. [Service boundary](M0_5_LOOPBRIDGE_FEASIBILITY.md#where-the-service-runs), [adapter map](M0_5_LOOPBRIDGE_FEASIBILITY.md#adapter-and-ownership-map), [transport comparison](M0_5_LOOPBRIDGE_FEASIBILITY.md#protocol-and-transport).

    Local agent or authorized human controller
        |  authenticated local channel, grants and lease
    Unprivileged LoopBridge in one graphical session
        |  typed adapters with scoped capabilities
        +-- Sway IPC / Wayland       windows, outputs, focus, permitted input
        +-- libatspi / D-Bus         accessible objects, actions and events
        +-- logind / XDG / kernel    session, launch and scoped OS facts
        +-- capture adapter          approved frames or view-only session

Future private VM transport and explicit remote access would reach the same policy and command model. The media path needs its own authorized lifecycle. A supported input path on one compositor or one transport does not establish support on another. [ADR 0002](../DECISIONS/0002-native-loopbridge.md), [ADR 0004](../DECISIONS/0004-desktop-and-human-observation.md), [ADR 0005](../DECISIONS/0005-security-and-transport.md).

## Comparative decision matrix

| Layer | First candidate | Bounded alternative | Defer or exclude |
| --- | --- | --- | --- |
| Linux base | Debian 13 minimal. Good compatibility and low cadence cost. | Ubuntu 26.04 LTS minimal if a required package or hardware target blocks Debian. | Fedora as a newer-stack diagnostic, with more frequent release qualification. Alpine for workloads that can accept musl and OpenRC divergence. Buildroot for appliances outside the general desktop baseline. |
| Desktop/window control | Sway/wlroots plus XWayland. The pinned IPC offers a tractable window/focus adapter. | GNOME/Mutter if it closes the actual blocker and offers a supported window/focus path. | KDE/KWin pending a specific advantage. Weston for backend isolation. Xorg as a legacy diagnostic only. Compositor fork or new shell after a documented need. |
| Semantics | AT-SPI through libatspi, joined with independently sourced window state when justified. | Explicit per-app adapter for a proven use case or separately approved visual/input fallback. | A generic DOM adapter, universal element coverage or a generic pixel-to-element map. |
| Capture and input | On-demand scoped frame or view-only wayvnc on the test session. Test compositor-mediated input and a separate trusted local human takeover path. | GNOME Remote Desktop modes where the session identity and control path can be proven. Use portal ScreenCast/RemoteDesktop and EIS where the selected backend supports each capability. | Always-on capture, public RFB/RDP listeners, unrestricted input devices and a permanent media protocol. |
| Control transport | Typed gRPC/Protobuf candidate over private UDS with peer and client identity. | JSON-RPC 2.0 with explicit local framing and schema if the gRPC spike fails on a gating constraint. | WebSocket/browser exposure, production mTLS pairing, direct vsock and proxy productization until a local contract works. |
| Updates and image | At M2, evaluate a Debian package manifest, signed apt inputs and a pinned build snapshot. | Compare an Ubuntu autoinstall-based workflow only if the base changes. | Shipping an image, a custom installer, atomic-update architecture or a production signing/rollback mechanism in M1. |

The matrix uses fit judgments with **medium** confidence. It weighs supported application compatibility, policy enforceability and maintenance more heavily than upstream installer size. [Linux comparison and source notes](M0_5_LINUX_FOUNDATION.md), [protocol and security comparison](M0_5_LOOPBRIDGE_FEASIBILITY.md).

## Five largest technical risks

| Rank | Risk | What could change the recommendation |
| --- | --- | --- |
| 1 | Unreliable window-to-tree correlation or insufficient semantic coverage across app versions and toolkits. | Fail if the controlled fixture cannot be mapped and acted on repeatably, or an ambiguous match can reach a different window. Track unsupported and partial trees separately in GTK, Qt, Firefox/Chromium, Electron and an office app. |
| 2 | Headless capture, authorized input and human takeover may fail in the same session. | Demonstrate a headless synthetic output and a viewer that attaches to that output. Prove real human input reaches that session, preempts agent input and releases held input. If no documented path satisfies this, compare one compositor alternative. |
| 3 | Ambient session permissions let clients bypass Bridge policy or leak secrets. | Demonstrate that unenrolled and isolated clients cannot use the Bridge or reach raw desktop/bus endpoints, and that snapshots, streams and logs honor independent grants. Block privileged or remote paths until proven. |
| 4 | Races between focus, element lifetime, revocation and command delivery. | Force focus changes, app restart, lease expiry and disconnect during requests. No command may mutate a different target. Prove bounded cancellation and expose ambiguous outcomes without automatic mutation retries. |
| 5 | Rendering, upstream support and redistribution costs could make the stack hard to ship. | Record renderer and VM dependencies, assess later physical hardware with the open-source firmware policy, verify per-package security coverage, then demonstrate a verifiable patched rebuild and rollback before public distribution. |

### Unresolved choices and their implications

- Which compositor, input backend and session mode provide a reliable same-session takeover without granting broad access to the agent? This is the main desktop selection gate.
- Can a supported adapter correlate multiple windows from the same PID, including native Wayland and XWayland, without guessing? Ambiguous correlation limits which apps can receive semantic control.
- Which activation settings are needed for the pinned GTK, Qt, Electron and browser packages? A single successful fixture validates a narrow capability, while the compatibility matrix establishes practical coverage.
- Can the chosen .NET and Python client stacks preserve one contract while the server obtains accepted-socket peer credentials? Failure may change the RPC/framing choice and how local clients are isolated.
- Which physical devices work with the open-source image policy? What baseline limits for memory, storage and latency are viable after measurement? Driver/firmware gaps or unsustainable overhead can constrain supported targets or require revisiting the base.
- Which packages receive security maintenance for the entire release horizon, and which source archives must the project retain? The future product image size, virtual GPU compatibility beyond the reference environment, exact archive coverage and rollback strategy remain open. These affect M2/M4 qualification and do not block the first M1 probe.

## Proposed M1 experiment sequence

This is a proposed subdivision of the existing [M1 roadmap gate](../ROADMAP.md#m1--agent-native-desktop-proof). Keep M1 on an existing maintained Linux desktop. Keep M2 for the first bootable environment image and M3 for hardened external interoperability and handoff. No change to the milestone definitions is proposed. For each experiment, record package versions, session and renderer configuration, expected and observed results, and sanitized diagnostics. Use local fixtures and do the tests with no external account or service.

| Experiment | Smallest useful demonstration | GO / NO-GO |
| --- | --- | --- |
| **M1-A — Semantic feasibility** | In one Debian 13/Sway session with one synthetic output and no viewer, open an unmodified GTK app such as GNOME Calculator. From a trusted local inspection process, identify the compositor toplevel and the accessible tree. Inspect a control and invoke one supported semantic action. Observe an event or refresh and check the expected state. Capture the evidence used to correlate the window. | GO if the same fixture succeeds across three clean app launches, and a handle from a closed/restarted instance is rejected or recognized as invalid without affecting the replacement. Record whether the update was event-driven or required a refresh. NO-GO if there is no reliable mapping or meaningful action, or if dispatch can reach an unintended target. |
| **M1-B — Authorization and events** | Connect a separately running, explicitly enrolled client through a private local UDS. Repeat the one action through a narrow API and subscribe to relevant updates. Use a second denied client and an expired target. Force disconnect and a stream gap. | GO if the permitted operation produces verifiable state, every denied or stale action leaves fixture state unchanged, cross-session or unenrolled requests disclose no protected data, and recovery either resumes from a valid cursor or requests a fresh snapshot. NO-GO if the service needs a privileged or ambient-auth bypass, or a stream silently masks lost state. |
| **M1-C — Fallback and human control** | Use an app or fixture with a documented semantic gap. With separate grants, request one frame and one conventional input action, then attach a view-only observer to the same session. Demonstrate independent human takeover. | GO if the gap is reported, frame/input scopes are distinct, unauthorized input and clipboard exchange are rejected, and after human takeover queued agent input cannot reach the new focus. Show successful human action on the same session and state refresh before any new lease. Verify zero active capture subscriptions and zero encoded frame increments for 30 seconds before attach and for 30 seconds after detach, without frame requests. NO-GO if the session depends on an observer, viewer access bypasses policy or takeover cannot preempt the agent. |
| **M1-D — Compatibility and reproducibility** | Have a second operator follow the documented setup on an existing eligible desktop environment. Record results for one native Wayland and one XWayland client, one less accessible app and supported software rendering. Include the negative test report. | GO if the documented end-to-end scenario and failures are reproducible, known limits are published and all accepted M1 demonstrations pass. Broader Qt/Electron/browser/office coverage is evidence for later selection, with partial or unsupported controls explicitly recorded. NO-GO for image work if the reference proof cannot be independently reproduced or any mandatory denial, fallback or takeover test fails. |

**First experiment proposal.** Start with M1-A on the pinned Sway and AT-SPI packages, using a known calculator state, a digit button and an independently verified displayed result. Collect the compositor window record, accessible action and state or event with timestamps and lifecycle evidence. Repeat after the app is closed and reopened. Use one synthetic output, no viewer and no RPC or packaging work. This isolates the window-to-element join and semantic mutation before committing to transport or viewer integration. Success is evidence for proceeding to M1-B under separate authorization. It is one part of the roadmap gate. [Debian GNOME Calculator package](https://packages.debian.org/trixie/gnome-calculator), [Sway IPC evidence](M0_5_LINUX_FOUNDATION.md#which-component-knows-what), [AT-SPI evidence](M0_5_LINUX_FOUNDATION.md#accessibility-as-the-semantic-layer).

For a blocked gate, classify whether the failure comes from toolkit exports, compositor/session behavior, transport or policy. Spend one bounded follow-up on the relevant alternative and run the same acceptance case. Ubuntu is the base alternative, GNOME/Mutter the desktop alternative and JSON-RPC the RPC alternative. Avoid changing two layers in the same comparison. If the follow-up still fails, record NO-GO and bring the blocker to maintainers before taking on a custom compositor, image or broader integration. Record comparative resource measurements in later experiments with agreed budgets. This study defines no unmeasured performance threshold.

## ADR proposals for later review

| Proposed record | Context and tentative decision | Evidence required before acceptance |
| --- | --- | --- |
| Linux reference base and distribution maintenance | Debian 13 minimal and a reviewed package set, with Ubuntu LTS as the documented fallback. Reuse distribution tooling and retain the standalone OS and licensing boundaries. | Pin versions, show that the maintained base supports M1, identify coverage gaps and outline how a patched image can be built and qualified before M2. |
| Desktop integration and monitorless session | Wayland with an initial Sway adapter, XWayland compatibility, AT-SPI and optional capture. Keep window authority, accessible semantics and human control separate. | Pass M1-A/C/D on the chosen session and document one supported conventional input path, one headless renderer, capture shutdown and actual human takeover. |
| Session authority, command model and RPC | Unprivileged session service, explicit identity plus scoped grants and a transport-neutral conceptual API. Evaluate typed gRPC and a framed JSON-RPC fallback. | Pass M1-B/C, document peer-identity handling, stale targets, event gaps, revocation and the supported client/toolchain trade-offs. |

These proposals extend the [accepted decisions](../DECISIONS/README.md). Two design tensions require proof rather than a policy change. Desktop-wide capture and input can conflict with resource-scoped access, so constrain the fixture session and withhold capabilities that the backend cannot enforce. A Debian installation path that includes closed firmware may support more devices, while ADR 0003 constrains what the official image may distribute. Maintain the supported hardware boundary until maintainers decide how to handle such devices. The README's external client can be a separately running client on the roadmap's local-only M1 channel. External host access, remote opt-in and production interoperability can follow their existing gates.
