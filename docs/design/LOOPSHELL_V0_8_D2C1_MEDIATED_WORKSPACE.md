# V0.8-D.2C.1 — Mediated workspace document creation

The opt-in LoopBridge profile implements one capability, `workspace.document.create`.
It publishes one regular file per enrolled resource from 1–1,024 bytes of UTF-8 text.
Clients use opaque resource identities. The adapter treats bytes as inert data and
retains them as supplied, including Unicode composition and line endings. Discovery,
editing, deletion and arbitrary execution are outside this profile.

## Authority and compatibility

- The Registry records the executor's binding to a principal and the objective's
  acceptance. Admission checks the exact accepted objective revision and the
  available executor. Objective text stays in the Registry.
- A trusted provisioner grants `authorize` to the admitting principal and
  `perform` to the principal bound to the executor. Both grants name the exact
  capability, resource, executor, accepted objective revision, attempt and SHA-256
  payload digest. The admission binds the executor revision, both grant generations
  and the minimum of the grant deadlines, objective deadline and requested TTL.
  The supervisor obtains independent `step`, `continue`, `pause` and `cancel`
  grants for the same scope. `status` and `audit` each need a separate grant.
  A supervisor can drive an attempt for an enrolled performer with the exact
  `perform` grant. All request actors come from authenticated connections.
- The client proposes the attempt ID so the trusted provisioner can bind the grants
  before admission. LoopBridge allocates a separate durable operation ID.
  Resource enrollment, approved resource pins and capability grants enter through
  the in-process trusted interface. The client receives no private descriptors.
- The profile reuses Registry authentication, the pinned verifier policy,
  `registry/1` and the Registry write lock. It has a separate socket, SQLite
  application ID `0x4c4f5745`, schema and ledger. The Registry tables and effect
  tables share that new database so Registry state and effect authority can be
  checked under one lock order. The database uses `STRICT` tables,
  foreign keys, rollback journal `DELETE` and `synchronous=EXTRA`. Startup
  requires its exact schema, integrity checks and the original `DatabasePin`.
  Historical Registry and `execution/1` and `execution/2` databases keep their
  own schemas and services. The profile performs no migration.
- The fixture holds an exclusive directory lock. Its private root and resources
  use the [trusted-directory discipline](LOOPSHELL_V0_8_D1C2_OPERATIONAL_REGISTRY.md#banco-e-recuperação).
  Bootstrap enrolls a fresh service-owned `0700` directory per opaque resource
  and returns its device/inode pin. The supervisor retains the resource,
  database and Registry policy pins independently of the data being reopened.
  The resource pin recorded in the attempt must also match. The local endpoint
  admits the service UID. An explicitly provisioned `CrossUIDIngress` uses the
  existing peer admission and separate ingress path. UID admission and
  individual LoopBridge authentication remain distinct.

## Capability adapter

| Boundary | Fixed adapter operation |
| --- | --- |
| Request validation | Check text type, UTF-8 encoding and byte length. Reject empty text, NUL and unpaired surrogates. The broker also rejects configured synthetic credentials carried as content. |
| Resource identity and preconditions | Open the enrolled directory with descriptor-relative, no-follow checks. Compare its pin, check the final name is vacant, check the staged bytes against the approved digest, and recheck the verified file version at the fence. |
| Preparation | Create an operation-specific hidden regular file with exclusive creation and mode `0600`. Write bounded bytes, synchronize the file and directory, then record the file's device and inode in SQLite. |
| Application | Invoke Linux `linkat` via `os.link` with directory descriptors and no symlink following. The fixed destination is `document.txt`. An existing entry causes failure without changing it. |
| Independent inspection | Reopen the final name without following symlinks. Verify both names resolve to the pinned regular inode with the expected device, owner, mode, two links, exact size and SHA-256. Check the names and metadata around the bounded read. |
| Confirmation and reconciliation | Synchronize the independently opened file and its directory and recheck attribution. SQLite records the observation and its outcome. Recovery uses the same inspection of retained evidence. |

The staging link stays private and is retained until the disposable fixture is
removed. It associates the inode with the durable operation and pins it against
ordinary inode reuse. A file with identical bytes and a different inode is
conflicting evidence. The source name is generated by the service. The final
name is fixed by the adapter. The profile loads a single built-in implementation.

## Attempt and effect state

| State | Supervision or effect | Durable transition |
| --- | --- | --- |
| `ready` | `paused`, effect `none` | Admission records the grant generations, operation ID, digest and payload size. Document bytes remain in bounded process memory until preparation. |
| `preparing` | `stepping`, `flowing` or `pause_requested`, effect `none` | A control command permits the preparation worker. A pause drains this bounded step. |
| `prepared` | `paused` after a step or pause, `flowing` after continue, effect `none` | Synchronized staging file and durable inode attribution. A step from `ready` stops here. |
| `dispatched` | `stepping` or `flowing`, effect `pending` | Durable publication intent. A pause that wins before the effect boundary returns the attempt to `prepared`. A subsequent explicit advance can issue new intent. |
| `cancelled`, `revoked`, `expired`, `failed`, `interrupted` | `stopped`, effect `absent` | A definite decision or durable history proves this operation did not publish. An occupied destination can belong to another operation. |
| `completed` | `stopped`, effect `confirmed` | Live inspection and synchronization succeeded. SQLite committed observation and confirmation. |
| `reconciled` | `stopped`, effect `confirmed` | Startup confirmed the effect from retained evidence and recorded recovery. The result makes no assertion of current execution authority. |
| `uncertain` | `stopped`, effect `unknown` or `observed` | Missing or conflicting evidence leaves the effect unknown. A verified file with incomplete synchronization records the observation and preserves uncertainty. Only recovery with sufficient evidence can promote this state to `reconciled`. |

`step` drives one stage, and `continue` drives the two-stage plan subject to a
new check at each boundary. A pause or cancellation that wins before publication
prevents the worker from crossing. Grant removal or replacement takes effect
under the same mutex. Expiry and grant invalidation become durable outcomes when
a worker checks authority. A paused snapshot is a progress observation and may
precede that check. An expired attempt cannot acquire publication authority
through a new command.

The lock order is the Registry identity/policy mutex, Registry lock, and SQLite
transaction. The final fence holds that order for a pinned database read and
bounded resource metadata checks. It rechecks the authenticated driver, the
accepted objective and executor binding, and all pinned grants. The last UTC
sample follows those checks and must be strictly before every applicable
deadline. The service immediately hands off to the single no-replace syscall
under the same mutex. Expiry is ordered at that final sample. Scheduling and
the syscall can delay visibility after the decision. The syscall is the only
filesystem mutation under the authority lock.
Payload writes, hashes, filesystem synchronization and independent inspection
all run outside it. The profile assumes a responsive local filesystem and
cooperative stage boundaries.

The final name becomes visible at the successful hard link. The service confirms
filesystem persistence only after independent observation, successful file and
directory `fsync`, and revalidation of the pinned names. The subsequent SQLite
commit establishes the durable confirmation record. These are separate
boundaries. Before the link, changes to pause, cancel and authority can stop it.
Once the syscall is entered, pause and cancel return `effect_boundary_closed`
while evidence is pending. Confirmation can proceed even if grants are revoked
or expire after the decision. A receipt never authorizes further work.

## Interruption and uncertainty

Startup holds the fixture lock and reconciles before opening ingress. A pending
attempt that never reached durable publication intent becomes
`interrupted/absent`. A pending publication intent with missing, displaced,
conflicting or unsynchronized evidence is uncertain. A missing final name
alone cannot resolve that intent. A definite occupied-destination result in the
live path proves this operation's absence. Ambiguous application errors retain
their own audit evidence. A successful inspection during recovery records
`reconciled`. Confirmed history remains intact. No recovery path invokes
application or reissues capability grants. The pinned Registry policy remains
a separate bootstrap input.

The profile covers process loss with retained pinned storage, including
`SIGKILL` on either side of the link. Linux file and directory synchronization
is required for confirmed persistence. SQLite and filesystem updates have
separate failure windows. Host power loss, device failure, filesystem rollback,
privileged interference, a compromised service UID and cross-UID isolation
remain outside the local qualification. The guarantee is creation without
replacement in the enrolled fixture, with conservative evidence-based recovery.

## RPC and reference client

The profile accepts `registry/1` and `workspace-effect/1` over the existing
8,192-byte Unix JSON-RPC framing. IDs are 32 lowercase hexadecimal characters.
Revisions are integers from 1 to 2⁵³−1. Audit cursors also accept zero.
The TTL is an integer from 1 to 300 seconds. Fields are exact.

| Method in `workspace-effect/1` | Parameters |
| --- | --- |
| `auth` | `credential` |
| `effect.authorize` | `request_id`, `attempt_id`, `executor_id`, `objective_id`, `accepted_revision`, `capability`, `resource_id`, `ttl_seconds`, `content` |
| `effect.step`, `effect.continue`, `effect.pause`, `effect.cancel` | `attempt_id`, `expected_revision`, `request_id` |
| `effect.status` | `attempt_id` |
| `effect.audit` | `attempt_id`, `after_revision` |

A command returns `id`, `revision` and `kind` for its historical receipt.
Use `status` for the current attempt, supervision and effect state. Use
`audit` for the scope, digest, actor IDs, deadlines, operation ID and a
page of up to 12 ledger events. Continue at `next_after` when it is present.
Private paths, inode pins, credentials, objective text and document bytes
stay out of the projections. The bounded fixture holds up to 64 resources,
128 attempts, 16 distinct control commands per attempt and 1,024 live grants.
The command budget reserves slots for a pause and cancellation after advance.

Admission deduplicates by authorizer and request ID after checking the current
scope and Registry target. Divergent eligible requests conflict. A receipt's
TTL and payload identity are fixed at admission. Control deduplicates by
attempt, actor and request ID. Matching authorized repetitions retrieve the
original receipt, including after a lost transport reply. Replays perform
no work. A separately initiated operation requires its own explicit exact
grants and a new attempt and request ID.

The profile uses the Registry errors and adds `authorization_expired` (−32060),
`destination_exists` (−32061), `resource_unavailable` (−32062) and
`effect_boundary_closed` (−32063).

For a disposable service harness, use `enroll_workspace` and
`initialize_workspace_database` once, prepare the pinned Registry manifest,
then call `serve_workspace` with the original pins. The context yields the
endpoint, the trusted capability grant interface and the Registry policy
control. Register and accept via `registry/1`. Construct a `Scope` with
the exact attempt and payload digest and configure the permissions above
with `effects.grant(principal, permission, scope, expires_at=...)`.
The [integration fixture](../../tests/test_workspace_effect.py) performs
that setup and drives the profile through real RPC.

Use `python3 -B -m tools.workspace_effect --help` for the client. Its
`authorize` command reads content from standard input and the bearer from
a masked terminal prompt. An explicit `--service PID UID GID` checks the
expected kernel peer for the later cross-UID profile. The local default
checks the service UID against the caller's UID.
